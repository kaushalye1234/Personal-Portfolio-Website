Inside the application

About these screenshots

Screens captured from the actual desktop frontend rendered in a browser. Products and API responses are synthetic. No shop database, payments, printers, or real customer records were used; the screenshots do not certify the native Electron runtime.

The context

The problem worth solving.

A sale is only one part of running a shop. Cashiers need a focused transaction flow, while stock, customers, suppliers, and reporting must stay connected to the same retail records.

At the counter

Product search, barcode-assisted entry, cart calculations, discounts, checkout, receipts, and returns.

Behind the counter

Inventory, staff and cashier workflows, customers, suppliers, purchase orders, and reporting.

Across the system

Authenticated API access, role-based authorization, backup and synchronization utilities, and Windows packaging.

How it fits together

Behind the interface.

Electron desktop client
Authenticated REST API · Node.js / Express
MongoDB / Mongoose

A technical decision

The desktop client handles the cashier interaction; the API centralizes business operations and retail records. This separates the interface from data access and gives different screens a shared service layer.

Testing & evidence

The repository includes cashier unit tests, backend parser tests, Playwright configuration, and electron-builder packaging. These demonstrate implementation and test tooling; they are not evidence of a fresh full-system verification run.

What I would verify next

Sales and stock consistency, recovery verification, isolated tests, and repeatable releases remain engineering priorities. Backup tooling needs a verified restoration exercise before operational reliance.
